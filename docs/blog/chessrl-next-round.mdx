In the [first post](/blog/chessrl-alphazero-single-gpu) I trained a small chess network (1.29M parameters) from nothing but the rules of chess, on the RTX 4090 in my desktop. It reached roughly the level of Stockfish limited to 1400 Elo, but it took two weeks. I suspected that most of that time was wasted.

## How this round was done

Most of the work in this round was done by an AI agent: Claude, Anthropic's model, running in Claude Code. I gave it a general task: make the Elo go up, and reduce the training time needed to get there. I also gave it the code. Open-ended tasks with a clear number to improve are something LLM agents have become very good at, and this round shows how far that goes.

The agent read through the training code and found the problems described below. It wrote the fixes, the transformer, and the tools to evaluate and monitor runs. It planned and ran the experiments, kept a lab log, and found the FP16 bug described later. My part was the goal, a few ideas to test (growing the network during training, switching to a transformer), and decisions along the way: which results to trust, when a question was answered and the experiments should move on, and which run to extend. The agent also wrote the first draft of this post. Below, "I" means me and "we" means the agent and me.

One rule applied to every experiment: each change gets its own training run on a single RTX 4090, and every run is measured the same way. The question was how much faster the same setup can learn chess if we improve how it learns, and not only how fast the code runs.

## How the system learns

The program learns by playing against itself (self-play). To choose each move, it runs a search called Monte Carlo tree search (MCTS). The search is made of simulations: each simulation follows a promising line of moves one step deeper and asks the neural network about the position at the end of it. The network answers with a policy (how promising each legal move looks), a value (how likely a win, a draw or a loss is) and an estimate of how many moves are left. After a few hundred simulations, the search picks better moves than the network would alone.

Every position played is saved with what the search found and the final result of the game. A separate process, the trainer, reads these saved positions in batches of 2,048 and trains the network to predict them. One batch is one training step. Every 500 steps the new network is converted with TensorRT, NVIDIA's library for running networks fast, into an "engine" that runs in 16-bit floating point (FP16). Self-play picks it up and keeps going. The trainer itself uses PyTorch.

## How we measure strength

Every 30 minutes, a separate process takes the newest network and rates it. It plays 96 games against reference opponents whose strength is known: the two closest to the network's current level, 48 games each, from fixed openings, with each opening played once with each colour. In these games the network always searches **100 simulations per move**, whatever its training run uses, so the rating measures the network and not the size of its search. The reference opponents are a player that moves at random, a player that always captures when it can, and several versions of Stockfish with reduced strength. Their ratings were set once, in a tournament among themselves, with random play fixed at 0 Elo. The network's rating is the one that best explains its results against them, with an uncertainty of about ±40 Elo. We call this the rating ladder.

This scale is only comparable to itself: it is not a FIDE rating, and not the rating Stockfish reports for its limited settings. A single rating is also noisy, so we compare trends and repeated runs, not single points. Each network also solves the same 1,000 Lichess puzzles, also with 100 simulations per move. The puzzles were the first metric to show a problem when something went wrong.

## Change 1: better training targets

Reading through the original training loop, the agent found three problems.

1. **The policy learned from the wrong target.** The policy was trained to predict the one move that was played. The search knows much more than that: how many simulations it spent on each move. Those visit counts form a probability distribution over all the moves, and AlphaZero trains the policy on that distribution, which is a better target than a single sampled move. The code threw it away. Now each saved position keeps the 84 most-visited moves with their counts (more than 99% of all visits), and the policy is trained to match them.
2. **The search used the wrong value output.** The network has two value outputs: one trained on the final result of the game, the other on the search's own estimate of the position. The search used the second one. Early in training this goes in circles: an untrained network searches, the search produces estimates, and the network learns to copy them. The only real information comes from checkmates the search happens to find, and 98.7% of those targets were close to one third each for win, draw and loss, which says nothing. Switching the search to the output trained on game results fixed it.
3. **Every move was played with randomness.** To explore, self-play picks moves at random in proportion to the search's visit counts, and the code did this for the whole game. Games were long and noisy, and their results said little about the quality of the moves. AlphaZero only does this in the opening. We now do it for the first 30 plies (half-moves) and play the search's best move after that. We also let the engine resign lost games, and check that this is safe by playing 10% of them to the end anyway. Finally, only a quarter of the moves get a full 800-simulation search and are saved for training. The others get a quick 100-simulation search that only moves the game forward, which makes games faster (this is called playout-cap randomisation).

To see which change mattered, we ran the new recipe with each one removed:

<AblationChart />

The policy target matters most: without it the agent is about 700 Elo behind after 6M positions, and the gap does not close. The value-output change speeds up the start (250 Elo behind at 2M positions without it), but the run without it catches up by about 10M positions. Limiting randomness to the opening made no measurable difference. Random moves throughout the game give more varied data early on, which seems to cancel out the noisier game results.

We also improved the infrastructure: new engines are loaded into the running self-play instead of restarting it (a restart threw away every game in progress), the trainer no longer waits 410 seconds before its first step, and engines are built in the background. A run with only these changes was faster in the first hours but ended at the same level as the original. Faster code produces more games, not better learning.

## Change 2: a small transformer instead of a ResNet

The original network is a ResNet: 4 blocks of 64-channel convolutions, the kind of network AlphaZero used, scaled down. We replaced it with a small transformer of 0.81M parameters. Each of the 64 squares becomes a token, and attention lets every square take information from any other square in one step, where a convolution only looks at neighbouring squares.

<EncoderDiagram />

The transformer is 32% slower per self-play position, because attention over 64 tokens costs more than small convolutions at this size. It still wins clearly. After the same number of positions it plays 450 to 580 Elo stronger than the ResNet, and at the same rating it solves far more puzzles (47% against 23 to 25% after 4,000 training steps). Chess has many long-range relations, like a rook and the far end of its file or a bishop and its diagonal, and attention handles them directly.

## Change 3: a cheaper search

With a stronger network, 800 simulations per saved move looked expensive. Halving the search used in training (400 simulations for saved moves, 50 for the quick ones) doubles the number of games per hour. Ratings are still measured with 100 simulations per move:

<SearchBudgetChart />

Per saved position, the cheaper search learns less in the middle of training, because its visit counts are noisier targets, and catches up by about 8M positions. Per hour, it reaches every level first: above 1,000 Elo at 2.5 hours instead of 3.4, and 1,800 at 6 hours instead of 8. The lighter line is the 800-simulation recipe run a second time with a different random seed. The two runs stay within about 100 Elo of each other, which shows how much chance alone changes.

A second 400-simulation run with another seed landed almost on top of the first one (1,503 against 1,504 at 3.5 hours, 1,619 against 1,614 at 4 hours), so the gain is not luck. Halving the search again does not help: with 200 and 25 simulations, the run fell 100 to 250 Elo behind from hour 3 on and stopped improving at about 1,350 to 1,400. It was also far behind per position (1,343 against 1,822 at 10M positions). For a run of about a day, 400 is the right amount.

The cheaper search reaches its plateau sooner, but the plateau is not higher. Continued to 17 hours, the 400-simulation run levelled off at about 1,860 to 1,900, roughly 60 Elo below the 800-simulation run. Noisier targets seem to cost a little at the top. This comes back in the section on scaling.

## The bug that looked like a collapse

After about 17 hours, the transformer run started getting worse. Puzzles solved fell from 73% to 64%, there were more draws, games got longer, the training loss went up, and the rating dropped from about 1,900 to about 1,750. Self-play training has a known failure where the network gets stuck learning from its own bad games, and this looked exactly like it.

The first suspects were a learning rate too high for this stage of training, a network too small, and badly calibrated resignations. The agent tested them by starting three copies of the run from the same checkpoint, each with one change: a decaying learning rate, a bigger network, and recalibrated resignations. All three kept getting worse, so the cause had to be something the three copies shared. The main candidate was the TensorRT engine, the converted copy of the network that self-play uses.

The trainer uses PyTorch with mixed precision, which computes squares and their sums in 32-bit floats. Self-play, the rating games and the puzzles all use the TensorRT engine built from the same weights, which runs in FP16, where the largest number is 65,504. The transformer uses a normalisation layer called RMSNorm: it divides each token by the square root of the mean of its squared values, `x / sqrt(mean(x²))`. Without weight decay (explained below), the values inside the network had been growing during the whole run:

<ActivationChart />

Once a value passes 256, its square passes 65,536, which is too large for FP16 and becomes infinity. Dividing by infinity gives zero, so that square's token is replaced by zeros, and no error is raised. We compared the TensorRT engine with PyTorch on the same 256 positions: how often both pick the same best move, and how different their move probabilities are (KL divergence, where 0 means identical):

| training step | same best move | difference between move distributions (KL, mean / 95th percentile) |
|---|---|---|
| 10k to 30k | 99.2 to 100% | 0.0000 / 0.0001 |
| 40k | 98.8% | 0.071 / 0.0001 |
| 45.5k | 96.5% | 0.216 / 1.31 |

So from about step 40,000, a growing share of positions was played by a different policy from the one being trained, and every game, every training target and every rating came from that faulty copy. The fix is one line: divide each token by its largest value before squaring. RMSNorm gives the same result whatever the scale of its input, so this changes nothing except avoiding the overflow. Rated again with fixed engines, the checkpoints that seemed to decline were not declining:

| training step | broken engine | fixed engine |
|---|---|---|
| 30k | 1,839 to 1,898 | 1,947 ± 40 |
| 40k | 1,904 | 1,892 ± 40 |
| 45.5k | 1,750 to 1,790 | **1,989 ± 40** |

The network itself never got worse; only the copy used to play did. The first post ended on the same advice: test every boundary between two versions of the same computation. Here the boundary was between the network we train and the engine that plays. A script, `trt_parity.py`, now compares a checkpoint with its TensorRT engine in a few seconds.

The fix removes the overflow but not its cause. Nothing kept the weights small. The optimizer (Adam) had no weight decay, which is the usual term that pulls every weight slightly toward zero at each step. In the transformer run, the overall size of the weights (their norm) grew from 105 to 192, and the values inside the network grew with them. One last run added weight decay (AdamW, 0.05, on the weight matrices only) to the 400-simulation recipe. It is the violet line in the chart above. Over 18 hours its weight norm stayed around 105, while the same recipe without weight decay passed 220, and its largest value reached 80 at step 70,000 instead of passing 440. It ended at the same level: about 1,860 to 1,890, 20 to 50 Elo below the run without weight decay, with the same puzzle accuracy.

Weight decay is still worth keeping, because it keeps the engine within FP16 range. It also rules out one explanation for the plateau. With normalisation layers everywhere, growing weights make each training step change the network less, so the network could have been slowly freezing. With the weights held at a constant size, it plateaus at the same level anyway.

## Elo per hour and Elo per step

Everything above is measured per hour of training, because the task was the fastest route to a strong network on one GPU. But a comparison per hour only covers the length of these runs, about a day. Elo per training step is also worth watching: how much each training step improves the network, whatever the step costs. Measured that way, the order is reversed:

<StepChart />

To reach about 1,400, an 8-layer transformer (1.47M parameters, 800 simulations) needed about 5,500 training steps. The 4-layer one needed about 8,000 with 800 simulations, and about 12,000 with 400. Per hour the order flips back, because the steps do not cost the same: with 400 simulations a run does about 4,000 steps per hour, with 800 about 2,100, and the 8-layer network about 640. Its self-play is about 40% slower on the same machine, and this run also ran on a slower machine.

This matters for longer runs because of the shape of these curves: they rise quickly, then level off. A recipe with cheap steps wins the early part by taking more of them. In a long enough run, what counts is the level where the curve flattens, and recipes that gain more per step tend to keep climbing for longer. So a steeper Elo-per-step curve usually pays off as training gets longer, even when each step is slower. The 400-simulation run already shows this on a small scale: it was ahead of the 800-simulation run for the first 8 hours, then levelled off about 60 Elo below it.

The two changes that make steps slower but more useful are therefore the natural next steps: more simulations per move, and a bigger network. The plateau at about 1,900 to 1,950 also points that way. The changes that kept the 0.81M network and its search as they were (a decaying learning rate, cleaner resignation decisions, weight decay) all left it where it was.

Growing the network during training is one way to get a bigger network without paying for its slow steps from the start: begin with a small, fast network and add layers when progress slows down. We tried it. The new layers start out passing their input through unchanged, so the grown network plays exactly like the old one at first and then learns to use the new layers. We grew the ResNet, a transformer starting from 2 layers, and a transformer that had reached its plateau (from 4 to 8 layers). It does not work yet: every grown run ended level with the network that was never grown, or at most about 90 Elo ahead, which is within the difference between two seeds. An 8-layer network trained from the start learns more per step, so the extra layers are useful. We don't know yet why adding them later does not give the same benefit.

## Next steps

1. **Scale up those two changes**: more simulations per move and a bigger transformer, in runs long enough for the gain per step to make up for the slower steps. Ratings should then also be measured with more than 100 simulations, because a small search may hide differences between strong networks.
2. **Find out why growth does not work yet.** It would give a bigger network's gain per step without its slow start.
3. **Use weight decay by default.** It keeps the network within FP16 range at almost no cost.
